Introduction

You cannot make a system faster until you know what limits it. In this assignment you will take one training step of a large language model apart on a single GPU, find out where its time and its memory go, and learn the tools for finding that out: GPU timers, the GPU's own counters, and NVIDIA's profiler, Nsight Systems.

A GPU offers a program three resources:

  • compute: arithmetic operations per second (TFLOP/s);
  • memory bandwidth: bytes per second moved between memory and the cores (GB/s);
  • memory capacity: bytes that fit at once (GiB).

Throughout this assignment the question is the same: which resource is the limit here?

The model is OLMoE-1B-7B, a mixture-of-experts (MoE) language model from the Allen Institute for AI. It has 6.9 billion parameters, but any one token uses only 1.3 billion of them. That gap shapes almost everything about how the model performs, and you will meet it in all three assignments of this course:

AssignmentYou willGPUs
1Measure where time and memory go in a training step1
2Add data and expert parallelism, fine-tune the whole model, and compete on throughput1–8
3Serve your fine-tuned model with vLLM and SGLang, and study inference configurations1–8

You will not write any model code. The file olmoe/model.py is a complete and reasonably efficient OLMoE. Your job is to build a few small measuring tools, to measure, and to explain what you measure.

The assignment has four parts:

  1. One operation. You learn to time GPU code correctly, to bound how fast an operation can run with the roofline model, and to read the GPU's own counters.
  2. One forward pass. You examine a forward pass of the real model with Nsight Systems.
  3. One training step. You take a step apart: its forward pass, its backward pass and its optimizer, the memory they need, and two ways of trading time for memory, activation recomputation and micro batches.
  4. Predicting performance. You write a small model that predicts the time and memory of training steps you have never run.

Parts 1 and 2 are mostly a guided tour, in which you run things and study what they print. Parts 3 and 4 ask more of you. Expect to spend 10 to 20 hours in all.

Part 1: One Operation

Before profiling a model, you need to be able to measure one operation and to say what limits it. The operation in this part is the one that language models spend nearly all of their arithmetic on: a matrix multiply.

Timing GPU Code

When Python calls torch.matmul(a, b) on GPU tensors, the call returns almost at once. It has only enqueued a kernel, and the GPU runs the kernel later. Timing the call with a clock on the CPU therefore measures the time to enqueue, not the time to multiply. Here are three ways of timing the same multiply of two 8192 × 8192 matrices.

The first reads the CPU's clock before and after the call:

t0 = time.time()
c = torch.matmul(a, b)
t1 = time.time()

The second waits for the GPU to finish before it reads the clock again:

t0 = time.time()
c = torch.matmul(a, b)
torch.cuda.synchronize()
t1 = time.time()

The third does not use the CPU's clock at all. It puts a CUDA event before the multiply and another after it, and asks for the time between the two:

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
c = torch.matmul(a, b)
end.record()
torch.cuda.synchronize()
ms = start.elapsed_time(end)

On an L40 the three report:

1: no synchronize       0.043 ms
2: with synchronize     9.954 ms
3: CUDA events          9.647 ms

The first number is wrong by a factor of several hundred: it is the time Python took to hand the work to the GPU. The second is right, because torch.cuda.synchronize() blocks until the GPU has finished everything it was given. The third is right too, and it is the one we will use. A CUDA event is a marker placed in the GPU's queue. The GPU stamps it with the time at which it reaches it, so the time between two events is the time the GPU spent on the work between them, and nobody had to wait in the middle. That matters once you want to time the parts of something larger without disturbing it, as you will in Part 3.

Two more things can spoil a measurement. The first calls of anything on a GPU are slow, because libraries are loaded and memory is allocated, so throw some calls away before you measure. And, as you are about to find out, a GPU that has just been idle runs faster than one that has been busy for a second.

The Roofline

Every kernel does arithmetic, and it moves bytes between memory and the cores. An L40 can do at most 181 TFLOP/s of bf16 matrix arithmetic, and it can move at most 864 GB/s. So a kernel that performs F floating-point operations and must move B bytes takes at least F / 181e12 seconds, and also at least B / 864e9 seconds. Whichever is larger is its bound:

  • if the first is larger, the kernel is compute-bound;
  • if the second is larger, it is memory-bound.

The roofline puts both bounds on one plot. A kernel's arithmetic intensity is F / B, in FLOPs per byte, and the most TFLOP/s it can reach is

min(peak compute, intensity × peak bandwidth)

The two meet at the ridge point, 181e12 / 864e9 ≈ 210 FLOPs per byte. Below it a kernel is memory-bound, and above it compute-bound.

Take the matrix multiply C = torch.matmul(A, B) in bf16, two bytes per number, where A is [M, k], B is [k, n], and C is [M, n]. It performs M * n * k multiply-adds, which is 2 * M * n * k FLOPs. It must at least read A and B and write C: 2 * (M * k + k * n + M * n) bytes. As an example, take one of the attention projections of our model, a 2048 × 2048 weight matrix, applied to M = 16 tokens:

FLOPs      = 2 * 16 * 2048 * 2048                        = 134 million
bytes      = 2 * (16 * 2048 + 2048 * 2048 + 16 * 2048)   = 8.5 million
intensity  = 134e6 / 8.5e6                               = 15.8 FLOPs per byte

That is far below the ridge point, so this multiply is memory-bound: its 8 megabytes of weights have to be read however few tokens there are. The best it can do is 8.5e6 / 864e9 = 10 microseconds, at 15.8 × 864 GB/s = 13.6 TFLOP/s, a thirteenth of the GPU's peak. Give the same matrix 4096 tokens and the intensity is 819: now it is compute-bound, and could run at the full 181 TFLOP/s.

Notice what happened. M is a number of tokens and B is a weight matrix. With few tokens a layer is limited by the bytes of its weights, and with many it is limited by its arithmetic. This one observation will explain a great deal of what follows.

Three Regimes

There is a third regime, which the roofline does not show. Launching a kernel has a fixed cost of some microseconds, on the CPU and on the GPU. When the work is small enough, that cost is all there is: the kernel is overhead-bound, and neither resource is anywhere near its limit.

You can tell the three regimes apart without a model, because the GPU counts what it does. a1/regimes.py runs one workload of each kind for a few seconds, and samples the GPU's own counters while it runs:

(cos568) $ python a1/regimes.py
large GEMM, 8192^3            10.8910 ms  kernel running 100%  memory busy  16%  1411 MHz  280 W
add two 1 GiB tensors          4.8808 ms  kernel running  97%  memory busy  97%  2490 MHz  207 W
small GEMM, 64 x 2048 x 1024   0.0153 ms  kernel running  51%  memory busy   0%  2490 MHz  141 W

The first number on each line is the time of one call. From this output you can conclude a few things:

  • The large GEMM is compute-bound. A kernel is running all of the time, but memory is being read or written only 16% of the time: the arithmetic works out of the caches.
  • Adding two large tensors is memory-bound. There is almost no arithmetic to do, and memory is busy 97% of the time.
  • The small GEMM is overhead-bound. Half of the time no kernel is running at all, although the loop launches them as fast as Python can. The GPU is waiting for the CPU.

The counters come from NVML, the library behind nvidia-smi, through the GpuMonitor class in olmoe/prof.py. They average over up to a second, so they are only meaningful for a workload that runs steadily for a few seconds. Look at the last two columns as well, the clock frequency of the GPU's cores and its power draw. They are not the same on every line.

Nsight Systems

Nsight Systems (nsys) records every kernel the GPU runs and every CUDA call the CPU makes, on one timeline. To find your own code in that timeline, you mark regions of it with NVTX ranges: torch.cuda.nvtx.range_push("name") opens one and range_pop() closes it. The model already marks two regions in each MoE layer, router and experts, and train_step marks forward, backward and optimizer.

One thing about ranges is easy to get wrong. A range marks a stretch of CPU time, the time during which your code launched kernels. The kernels themselves run later. Nsight can project a range onto the GPU, which means taking the span of the kernels that were launched from inside it. That is the number you usually want.

The script a1/nsys.sh records a run of a1/profile_step.py and summarizes the recording. It is short, and at its heart are two commands:

nsys profile --trace=cuda,nvtx --sample=none --cpuctxsw=none \
    --gpu-metrics-devices=all \
    --capture-range=cudaProfilerApi --capture-range-end=stop \
    --output=reports/a1/NAME python a1/profile_step.py ...

nsys stats --report nvtx_gpu_proj_trace --report cuda_gpu_kern_sum --report cuda_api_sum \
    --format csv --output results/a1/NAME reports/a1/NAME.nsys-rep
  • --trace=cuda,nvtx records CUDA calls and kernels, and NVTX ranges.
  • --sample=none --cpuctxsw=none turns off sampling of the CPU, which we do not need.
  • --gpu-metrics-devices=all samples the GPU's hardware counters, 10,000 times a second. More about them below.
  • --capture-range=cudaProfilerApi records only between torch.cuda.profiler.start() and stop(). profile_step.py calls them around two steps, after loading the model and warming up, so the recording is small and shows the steady state.
  • nsys stats turns a recording into tables. nvtx_gpu_proj_trace is the projection of your ranges onto the GPU that was just described.

  • GPU ms/step is the span of the kernels launched inside ranges of that name. Ranges nest, so the rows overlap: layers.* contains layers.*.moe, which contains experts.
  • instances is how often a range of that name was opened in a step: once per layer for anything inside a layer.
  • GPU ops is the number of kernels and memory operations launched inside.
  • The ranges whose names start with CCCL are not yours. NVIDIA's own libraries mark some of their internals in the same way.

Now look at the first line of that transcript, and at the line under the table. Nsight can also record the GPU's hardware counters, the GPU metrics, but reading them needs a permission that the administrators of a machine must grant. When this was written, the cluster's nodes did not have it, and the script recorded without them. On a node that has it, the note does not appear, and the table has four more columns: the means of four counters over the time when the kernels of each range were running.

  • sm active is the share of that time in which the GPU's cores, its 142 streaming multiprocessors, had work to do. It is low when the GPU is waiting for kernels to be launched.
  • tensor active is the share in which the tensor cores were busy, the units inside each SM that do bf16 matrix arithmetic. It tells you how much of the GPU's compute a range is using.
  • dram read and dram write are the shares of the memory bandwidth that were in use for reading and for writing.

These are finer versions of the counters that regimes.py printed in Part 1: they are sampled every 100 microseconds, not once a second, so they can be attributed to a single layer, and they tell the tensor cores apart from the rest of the GPU. Without them nothing else changes, and the two written questions that use the GPU metrics say what to use in their place.

Part 3: One Training Step

A training step has three phases. The forward pass computes the loss, and keeps the activations that the backward pass will need. The backward pass computes a gradient for every weight. The optimizer, AdamW, updates every weight. See train_step in olmoe/train.py: it is about ten lines.

In this assignment the weights, their gradients, and AdamW's two moments are all stored in bf16, two bytes each. That is 8 bytes per parameter. For all 16 layers it comes to 51.5 GiB, more than the L40's 44 GiB, before a single activation is stored. A model that does not fit on the GPU can still be trained there by offloading: part of that state is kept in the host's memory, and moved to the GPU only while it is needed. Offloading is a valid way to train large models, but we will not consider it in this assignment. Instead, in this part we train only the first four layers (--layers 4, 1.9 billion parameters). The layers are identical in shape, so what you learn about four of them carries over. The experiments in Parts 3 and 4 use random weights and random tokens, so that they need no checkpoint.

Recomputation

The forward pass keeps activations for the backward pass, and their size grows with the number of tokens and with the number of layers. With enough tokens, they are what fills the GPU's memory.

Activation recomputation, also called checkpointing, keeps only the input of each layer. When the backward pass reaches a layer, it first runs that layer's forward again, to rebuild the activations, and then computes the layer's gradients as usual. Only one layer's activations exist at a time, and the price is that every layer's forward runs twice in each step. It trades compute for memory capacity.

A step with recomputation therefore has four kinds of work, and the rest of this part accounts for each of them separately: forward, backward, recompute, and optimizer.

Micro Batches and Gradient Accumulation

Recomputation is one way to make a step fit in memory. Here is a second one. It rests on a property of the loss.

Two different things are called "the batch" of a step, and from here on we keep them apart. The global batch is the set of sequences that one optimizer update is computed from, and the global batch size is how many sequences that is. A micro batch is the set of sequences that goes through the model in one forward and backward pass, and the micro batch size is how many sequences that is. So far every step has run its global batch as a single micro batch, so the two sizes were equal. They need not be.

The loss of a step is the average, over all tokens of its global batch, of each token's cross-entropy:

loss  =  (l_1 + l_2 + ... + l_N) / N

Here l_i is the cross-entropy of token i, and N is the number of trainable tokens in the global batch, the tokens that have a target. Every one of them weighs 1/N. The gradient of a sum is the sum of the gradients, so the gradient that the optimizer needs is

gradient  =  (gradient of l_1) / N  +  (gradient of l_2) / N  +  ...  +  (gradient of l_N) / N

That is a sum of N terms, and it does not matter in what groups they are computed. So split the global batch into micro batches, each a few whole sequences, and run the forward and the backward pass of one micro batch at a time. Each backward pass produces the terms of its own tokens, and PyTorch adds them to whatever is already in .grad. After the last micro batch, .grad holds the gradient of the whole global batch, and the optimizer steps once. This is gradient accumulation.

The argument needs two things, and you should be able to say why:

  • A token's loss depends only on the tokens of its own sequence. Nothing in our model connects one sequence to another: attention never crosses a sequence boundary, the router looks at one token at a time, and there is no batch normalization. A micro batch therefore computes l_i for its tokens exactly as the whole global batch would in a single pass.
  • Every token's loss is divided by N, the number of trainable tokens in the global batch, and not by the number in its own micro batch. This is why lm_loss in olmoe/train.py adds the cross-entropies up (reduction="sum") and divides by a count that you pass in, instead of taking the usual mean. With the mean, a token in a micro batch of few tokens would weigh more than a token in a micro batch of many, and when sequences have different lengths, micro batches of the same size rarely have the same number of tokens.

The update is then the same whether a global batch of 16 sequences runs as one micro batch of 16 or as sixteen micro batches of 1. It is the same up to rounding: floating-point addition gives slightly different results when the same numbers are added in a different order. The two gradients agree to several digits, not bit for bit, and the tests compare them with a small tolerance.

What does change is the cost. Only one micro batch's activations are alive at a time, so the memory that a step needs depends on its micro batch size, while the update depends only on its global batch. In exchange, the model makes several small passes instead of one large one. The optimizer still runs once per step.

One more observation, on which Assignment 2 is built. Nothing in the argument says that the micro batches must run one after another, or on the same GPU. Give each of several GPUs some of the global batch's sequences as its micro batch, let each compute the terms of its own tokens with the same 1/N, and add the results up: the update is the same again. That is data parallelism. Gradient accumulation spreads a global batch over time, data parallelism spreads it over GPUs, and the two can be combined.

Timing the Stages of a Step

How long does each layer take, in each of the four kinds of work? You can find out with CUDA events and two kinds of hooks.

A forward hook is a function that you attach to a module. PyTorch calls it every time the module's forward has finished, and passes it the output. A tensor hook is a function that you attach to a tensor. PyTorch calls it during the backward pass, when the gradient of that tensor has been computed.

Here is a small example that uses both. Its model has two stages, the linear layers first and second, and x goes through one and then the other. Each stage gets a forward hook, and that hook attaches a tensor hook to the stage's output:

first = torch.nn.Linear(8, 8)     # a model with two stages:
second = torch.nn.Linear(8, 8)    #     x -> first -> second -> loss
x = torch.randn(4, 8)

def watch(name, module):
    def forward_hook(module, args, output):   # called when the forward of `module` has finished
        print(f"forward:  {name} has finished")
        output.register_hook(tensor_hook)

    def tensor_hook(grad):                    # called when the gradient of `output` is known
        print(f"backward: about to enter {name}")

    module.register_forward_hook(forward_hook)

watch("first", first)
watch("second", second)

loss = second(first(x)).sum()
print("calling loss.backward()")
loss.backward()

This prints

forward:  first has finished
forward:  second has finished
calling loss.backward()
backward: about to enter second
backward: about to enter first

The forward hooks fire in the order of the stages. The tensor hooks fire in the reverse order, during loss.backward(): the backward pass goes through the stages from last to first, and the gradient of a stage's output becomes known at exactly the moment the backward pass is about to enter that stage. So the hooks give you the boundaries between the stages in both directions, and a CUDA event recorded at each boundary gives you their times.

Recomputation needs one more boundary. A recomputed forward is an ordinary forward of the layer, so its hooks fire again, but in the middle of the backward pass. olmoe/prof.py has a function for telling the two apart: in_backward() is true while a backward pass is running. A forward pre-hook, which PyTorch calls when a module's forward is about to start, and a forward hook then give you the start and the end of the recomputation. Register the forward hook with always_call=True, as in Coding Exercise 4: PyTorch stops a recomputed forward as soon as it has rebuilt what it needs, by raising an exception.
