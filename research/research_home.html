I build systems software for machine learning. Models keep growing and context lengths keep getting longer, but accelerator on-board memory is expensive, supply-constrained, and inelastic. How much of this expensive, packaged VRAM is actually needed for good performance when it is paired with a secondary pool of cheaper, commodity memory?

The answer depends on the application's memory access pattern and on the transfer bandwidth between memory tiers. For compute-intensive workloads—ML training, offline large-batch LLM inference (high throughput, low per-user interactivity) as used in RL post-training, image/video generation, and robotics inference—the main bottlenecks are compute throughput and memory capacity, not memory bandwidth. So at any moment, only a small working set needs to be in the accelerator's high-bandwidth on-board memory, and the remaining data can stay in a cheaper tier. The challenge is deciding what to prefetch, what to evict, and when, such that these asynchronous transfers overlap with computation to avoid dependency stalls.

On its own, this resembles classical prefetching and caching problems (e.g., Patterson et al., 1995; Cao et al., 1995). It becomes much richer for ML workloads. Classical formulations assume a fixed sequence of memory accesses; an ML workload has no single such sequence. Its mathematical structure leaves many degrees of freedom in how it executes without changing the result: micro-batch sizing, chunking along independent axes, task scheduling, recomputation, sharding, and parallelism, among others. Each choice yields an equivalent program with a different memory access pattern, as well as different computation and peer-communication costs. Under bounded memory and limited hierarchical transfer bandwidth, only some of these access patterns let data movement hide behind computation. As a result, the best way to execute a workload depends on how well its data movement can be hidden.

Our system, ShadowSpill, treats this as a single search problem. It builds many of these equivalent programs. For each, it plans data movement within the memory budgets and transfer bandwidth, agnostic to tensor semantics: every tensor is placed by when it is needed, not by what it is, letting data be kept, evicted, and prefetched in any combination. It then simulates every plan and runs the fastest.

The same system and techniques serve several goals:

  • Same performance, cheaper hardware. Match the performance of an HBM-centric setup with a memory hierarchy skewed heavily toward DDR, even with low hierarchical transfer bandwidth. In many practical settings, only a small fraction of total memory capacity can be budgeted for the 3–10× costlier HBM tier.
  • More throughput, same hardware. Within the same HBM budget, effective offloading makes faster execution plans feasible: it avoids recomputation that would otherwise be necessary, and it enables parallelism configurations that keep peer communication (e.g., in expert, context, or tensor parallelism) off the critical path.
  • Bigger workloads, same hardware. Train larger models or longer contexts than would otherwise be practical.
